# VS-001 — Discussion to AI-Proposed Task

Status: In Progress

Version: 0.1

Started: 2026-08-10

## Objective

Validate the core Cadence architecture through one end-to-end user journey:

```text
Login
  ->
Project Workspace
  ->
Discussion
  ->
Team Agent task proposal
  ->
Human confirmation
  ->
Task creation
  ->
Audit trace
```

## Architectural Rules

1. PostgreSQL/Supabase is the authoritative state store.
2. Authentication and Cadence authorization remain separate.
3. Browser clients do not perform authoritative cross-module writes.
4. Each module owns its state.
5. Team Agent never writes directly to Tasks.
6. Protected operations enforce RBAC server-side.
7. Material writes produce versioned domain events.
8. AI-generated state requires provenance.
9. Human confirmation does not bypass target-module permissions.
10. Correlation IDs trace the complete operation.
11. Retryable commands must be idempotent where required.
12. Changes affecting contracts or architecture are recorded in `CHANGELOG.md`.
13. Permission checks use permission codes rather than hard-coded role names.
14. The authenticated actor comes from `RequestContext.actorUserId`.
15. Read-model aggregation does not transfer authoritative ownership between modules.

---

## Acceptance Scenario

Given an authorised project member posts:

> Daniel, please finalise the syllabus by Friday.

Cadence shall:

1. Store the human message and version.
2. Emit `MessageCreated.v1`.
3. Create an AI run.
4. Create a pending task proposal.
5. Allow an authorised human to review the proposal.
6. Revalidate `agent.approve`.
7. Revalidate `task.create`.
8. Revalidate `task.assign` when an assignee is specified.
9. Create one authoritative task.
10. Record provenance to the originating proposal/message.
11. Emit `TaskCreated.v1`.
12. Make the task visible through `GET /me/tasks`.
13. Reconstruct the complete action through one correlation ID.

# VS001-03 — Project Workspace Read Model

Status: Complete

## Objective

Allow an authenticated Cadence user who:

```text
has an active membership in the requested project
+
has project.view
```

to retrieve the Project Workspace summary.

Endpoint:

```text
GET /api/v1/projects/{projectId}/summary
```

VS001-03 proves that authentication, project membership, RBAC and the Project Workspace read model work together through the live API.

---

## Authorization Flow

Current flow:

```text
Supabase authentication
  ->
Cadence identity
  ->
RequestContext
  ->
ProjectsService
  ->
RbacService
  ->
active project membership
  ->
role
  ->
permission set
  ->
project.view
  ->
ProjectWorkspaceReadRepository
  ->
Project Workspace summary
```

Authentication is not repeated inside the Projects service.

The authoritative actor is:

```text
RequestContext.actorUserId
```

The Projects service does not check:

```text
role == PROJECT_LEAD
```

Authorization is based on permission codes.

For this endpoint, the required permission is:

```text
project.view
```

---

## RBAC Behaviour

### No active membership

If the authenticated user has no active membership in the requested project:

```text
404 NOT_FOUND
```

is returned.

This intentionally avoids exposing the existence of protected project resources to non-members.

### Active membership without `project.view`

If the authenticated user is an active project member but lacks:

```text
project.view
```

the result is:

```text
403 PERMISSION_DENIED
```

### Authorized member

If the user has:

```text
active membership
+
project.view
```

the Project Workspace summary is returned with:

```text
200 OK
```

## Project Workspace Read-Model Calculations

The following rules define the VS001-03 read model.

### My Tasks — Pending

Count tasks where:

```text
project_id = requested project
assigned_to = logged-in Cadence user
status IN (open, in_progress)
```

Conceptually:

```sql
project_id = project
AND assigned_to = current_user
AND status IN ('open', 'in_progress')
```

---

### My Tasks — Overdue

Count tasks where:

```text
project_id = requested project
assigned_to = logged-in Cadence user
status IN (open, in_progress)
due_date IS NOT NULL
due_date < current time/date
```

Conceptually:

```sql
project_id = project
AND assigned_to = current_user
AND status IN ('open', 'in_progress')
AND due_date IS NOT NULL
AND due_date < now
```

---

### Blockers

Count active blockers where:

```text
project_id = requested project
status IN (open, monitoring)
```

Resolved blockers are not counted.

---

### Next Milestone

Select the earliest incomplete milestone:

```text
project_id = requested project
status != completed
target_date IS NOT NULL
ORDER BY target_date ASC
LIMIT 1
```

If no qualifying milestone exists:

```text
next_milestone = null
```

---

### Alerts

Return alerts where:

```text
project_id = requested project

AND

(
  user_id IS NULL
  OR user_id = logged-in Cadence user
)

AND dismissed_at IS NULL

AND starts_at <= now

AND

(
  expires_at IS NULL
  OR expires_at > now
)
```

A null:

```text
user_id
```

represents a project-wide alert.

A populated `user_id` represents a user-specific alert.

## Project Health Integration

Project Health is not stored on:

```text
public.projects
```

Current Project Health is stored in:

```text
public.project_health
```

Historical health changes are stored in:

```text
public.project_health_history
```

The Project Workspace reads Project Health as part of its summary but does not own Project Health state.

Conceptually:

```text
projects
  ->
project metadata

project_health
  ->
current health

Project Workspace
  ->
combined read model
```

## Project Health Schema Correction

During VS001-03 implementation, the initial repository incorrectly attempted to read:

```text
projects.health_status
```

The live schema does not contain that column.

The repository was corrected so that:

```text
public.projects
```

provides project metadata, while:

```text
public.project_health
```

provides current health.

This preserves the intended module/data boundary.

## Projects Service

The current service flow is conceptually:

```typescript
const access =
  await rbac.getProjectAccess(
    context.actorUserId,
    projectId
  );

if (!access) {
  throw new ProjectNotFoundError();
}

if (
  !access.permissions.includes("project.view")
) {
  throw new ProjectPermissionDeniedError();
}

return repository.getSummary(
  projectId,
  context.actorUserId
);
```

The service does not:

```text
authenticate JWTs
```

because authentication has already been completed.

The service also does not:

```text
check role == PROJECT_LEAD
```

because RBAC owns role-to-permission interpretation.

Project Workspace loading is a read operation.

```text

```

No authoritative state changes when the workspace is loaded.

```text

```

Domain events remain reserved for meaningful domain state changes.

```text

```


The normal role was not modified.

For the negative test, an isolated temporary role was created:

```text

```

with no permissions.

Bob's Alice Project membership was temporarily assigned to the test role.

```text

```

After verification:

```text

temporary test role deleted
normal role definitions unchanged
```
