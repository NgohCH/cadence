# VS-001 — Discussion to AI-Proposed Task

Status: In Progress

Version: 0.1

Started: 2026-08-10

Cadence was conceptualized and prepared by Ngoh Chee Hung.

## Objective

Validate the core Cadence architecture through one end-to-end user journey:

```text
Login
  ->
Project Workspace
  ->
Discussion
  ->
Team Agent task proposal
  ->
Human confirmation
  ->
Task creation
  ->
Audit trace
```

## Architectural Rules

1. PostgreSQL/Supabase is the authoritative state store.
2. Authentication and Cadence authorization remain separate.
3. Browser clients do not perform authoritative cross-module writes.
4. Each module owns its state.
5. Team Agent never writes directly to Tasks.
6. Protected operations enforce RBAC server-side.
7. Material writes produce versioned domain events.
8. AI-generated state requires provenance.
9. Human confirmation does not bypass target-module permissions.
10. Correlation IDs trace the complete operation.
11. Retryable commands must be idempotent where required.
12. Changes affecting contracts or architecture are recorded in `CHANGELOG.md`.
13. Permission checks use permission codes rather than hard-coded role names.
14. The authenticated actor comes from `RequestContext.actorUserId`.
15. Read-model aggregation does not transfer authoritative ownership between modules.

---

## Acceptance Scenario

Given an authorised project member posts:

> Daniel, please finalise the syllabus by Friday.

Cadence shall:

1. Store the human message and version.
2. Emit `MessageCreated.v1`.
3. Create an AI run.
4. Create a pending task proposal.
5. Allow an authorised human to review the proposal.
6. Revalidate `agent.approve`.
7. Revalidate `task.create`.
8. Revalidate `task.assign` when an assignee is specified.
9. Create one authoritative task.
10. Record provenance to the originating proposal/message.
11. Emit `TaskCreated.v1`.
12. Make the task visible through `GET /me/tasks`.
13. Reconstruct the complete action through one correlation ID.


Endpoint:


VS001-03 proves that authentication, project membership, RBAC and the Project Workspace read model work together through the live API.

## RBAC Behaviour

### No active membership

If the authenticated user has no active membership in the requested project:

```text
404 NOT_FOUND
```

is returned.

This intentionally avoids exposing the existence of protected project resources to non-members.

### Active membership without `project.view`

If the authenticated user is an active project member but lacks:

```text

```

```text
403 PERMISSION_DENIED
```

### Authorized member

If the user has:

```text
active membership
+
project.view
```

the Project Workspace summary is returned with:

```text

```

## Project Workspace Read-Model Calculations

The following rules define the VS001-03 read model.

### My Tasks — Pending

Count tasks where:

```text
project_id = requested project
assigned_to = logged-in Cadence user
status IN (open, in_progress)
```

Conceptually:

```sql
project_id = project
AND assigned_to = current_user
AND status IN ('open', 'in_progress')
```

---

### My Tasks — Overdue

Count tasks where:

```text
project_id = requested project
assigned_to = logged-in Cadence user
status IN (open, in_progress)
due_date IS NOT NULL
due_date < current time/date
```

Conceptually:

```sql
project_id = project
AND assigned_to = current_user
AND status IN ('open', 'in_progress')
AND due_date IS NOT NULL
AND due_date < now
```

---

### Blockers

Count active blockers where:

```text
project_id = requested project
status IN (open, monitoring)
```

Resolved blockers are not counted.

---

### Next Milestone

Select the earliest incomplete milestone:

```text
project_id = requested project
status != completed
target_date IS NOT NULL
ORDER BY target_date ASC
LIMIT 1
```

If no qualifying milestone exists:

```text
next_milestone = null
```

---

### Alerts

Return alerts where:

```text
project_id = requested project

AND

(
  user_id IS NULL
  OR user_id = logged-in Cadence user
)

AND dismissed_at IS NULL

AND starts_at <= now

AND

(
  expires_at IS NULL
  OR expires_at > now
)
```

A null:

```text
user_id
```

represents a project-wide alert.

A populated `user_id` represents a user-specific alert.

## Atomic Persistence

Migration:

```text
supabase/migrations/20260813000100_post_discussion_message.sql
```

PostgreSQL function:

```text
public.post_discussion_message(...)
```

The function atomically persists:

```text
messages
  +

  +
MessageCreated.v1
```

The domain event is stored as:

```text
event_type = MessageCreated
event_version = 1
aggregate_type = message
aggregate_id = new message ID
```

If validation, authorization, message creation, immutable-version creation, or event creation fails, the transaction must not leave a partial Discussion write.

---

## Authorization

Application authorization follows:

```text
authenticated Cadence identity
  ->
active project membership
  ->
project role
  ->
permission codes
  ->
message.create
```

An active project member without:

```text
message.create
```

receives:

```text
403 PERMISSION_DENIED
```

Permission codes remain the authorization primitive. The implementation does not hard-code role names.

---

## Defence in Depth

The Discussion PostgreSQL function performs a second `message.create` permission check immediately before persistence.

The function uses:

```text
SECURITY DEFINER
search_path = public, pg_temp
```

Execution is revoked from:

```text
public
anon
authenticated
```

and granted to:

```text
service_role
```

Browser clients must not invoke this persistence function directly.

---

## Validation

VS001-04 validates:

- message content is supplied as a string at the HTTP boundary;
- trimmed content is not empty;
- content does not exceed 20,000 characters;
- project IDs are valid UUIDs;
- optional thread-parent IDs are valid UUIDs;
- a supplied thread parent exists;
- the thread parent belongs to the same project;
- a deleted message cannot be used as a thread parent.

Content is trimmed before persistence.

## Per-Consumer Deliveries

VS001-05 adds:

```text
public.domain_event_deliveries
```

A delivery is identified by:

```text
event_id
+
consumer_name
```

This allows multiple consumers to process the same domain event independently.

For example:

```text

        |
        +--> Team Agent
        |
        +--> Notifications
        |
        +--> Project Health
```

One consumer may succeed, fail, or retry without changing another consumer's delivery state.

---

## Delivery Lifecycle

Delivery state supports:

```text

  ->

  ->

```

and:

```text

  ->

  ->

  ->

```

Delivery records track:

```text

last_error
```

---

## Atomic Claiming

Delivery claiming uses PostgreSQL:

```text
FOR UPDATE OF d SKIP LOCKED
```

through:

```text
public.claim_domain_event_delivery(...)
```

This allows concurrent workers to safely claim different available deliveries.

The default processing lease is:

```text
900 seconds
```

A successful claim receives a unique claim token.

---

## Claim Token and Lease Safety

Claim tokens prevent stale workers from completing or failing a delivery after another worker has reclaimed it.

Conceptually:

```text
Worker A claims delivery with token A
  ->
Worker A stalls
  ->
lease expires
  ->
Worker B reclaims delivery with token B
  ->
Worker A later tries to complete with token A
  ->
completion rejected
```

Expired processing leases may be reclaimed.

# VS001-06 — Human Proposal Review

Status: Complete

## Objective

Implement the human-review boundary for a non-authoritative pending Team Agent task proposal:

```text
pending proposal
  ->
authorised human review
  ->
agent.approve
  ->
confirm / edit / reject
```

VS001-06 deliberately stops before authoritative Task creation.

---

## API

Authenticated endpoint:

```text
POST /api/v1/projects/{projectId}/task-proposals/{proposalId}/review
```

Supported actions:

```text
confirm
edit
reject
```

The authenticated reviewer is always taken from:

```text
RequestContext.actorUserId
```

Client-supplied reviewer identity is not accepted as authority.

---

## Authorization

Proposal review requires:

```text
agent.approve
```

The permission is checked through project-scoped RBAC using permission codes rather than hard-coded role names.

Authorization is enforced twice:

```text
TeamAgentService
  -> agent.approve
  -> TeamAgentRepository
  -> PostgreSQL review RPC
  -> agent.approve revalidation
```

The database recheck provides defence in depth if access changes between application authorization and persistence.

---

## Review State Model

The original AI-generated proposal remains in:

```text
ai_proposals.payload
```

The final human-reviewed proposal is stored in:

```text
ai_proposals.reviewed_payload
```

State rules:

```text
pending
  payload = original AI proposal
  reviewed_payload = null

confirmed
  payload = original AI proposal
  reviewed_payload = copy of original AI proposal

edited
  payload = original AI proposal
  reviewed_payload = final human-reviewed proposal

rejected
  payload = original AI proposal
  reviewed_payload = null
```

This preserves AI provenance instead of overwriting the original proposal.

---

## Confirm

Confirm accepts the AI proposal as-is:

```text
pending
  ->
confirmed
```

The persistence operation copies the original AI payload into `reviewed_payload`, records the human reviewer and timestamp, and emits:

```text
AIProposalConfirmed.v1
```

Confirm does not create a Task in VS001-06.

---

## Edit

Edit stores a separate reviewed proposal:

```text
pending
  ->
edited
```

Human-reviewed values may change task proposal fields such as title and description.

The following provenance fields are immutable during review:

```text
source_message_id
source_message_version_id
```

The original AI `payload` remains unchanged.

Successful edit emits:

```text
AIProposalEdited.v1
```

---

## Reject

Reject transitions:

```text
pending
  ->
rejected
```

A rejected proposal keeps:

```text
reviewed_payload = null
```

while recording the reviewer and review timestamp.

Successful rejection emits:

```text
AIProposalRejected.v1
```

A rejected proposal cannot create a Task through VS001-06.

---

## Atomic Persistence

Migrations:

```text
supabase/migrations/20260816024841_team_agent_human_proposal_review.sql
supabase/migrations/20260816082249_fix_team_agent_review_column_ambiguity.sql
```

Primary persistence function:

```text
public.review_team_agent_task_proposal(...)
```

The operation atomically:

```text
locks pending proposal
  +
revalidates agent.approve
  +
updates review state
  +
records reviewer/timestamp
  +
emits review domain event
```

`FOR UPDATE` protects against two reviewers successfully transitioning the same pending proposal concurrently.

The function is restricted to trusted service-role execution and is not a browser/client API.
