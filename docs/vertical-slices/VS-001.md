# VS-001 —Discussion to AI-Proposed Task

Status: In Progress

Version: 0.1

Started: 2026-08-10

Cadence was conceptualized and prepared by Ngoh Chee Hung.

## Objective

Validate the core Cadence architecture through one end-to-end user journey:

```text
Login
  ->
Project Workspace
  ->
Discussion
  ->
Team Agent task proposal
  ->
Human confirmation
  ->
Task creation
  ->
Audit trace
```

## Architectural Rules

1. PostgreSQL/Supabase is the authoritative state store.
2. Authentication and Cadence authorization remain separate.
3. Browser clients do not perform authoritative cross-module writes.
4. Each module owns its state.
5. Team Agent never writes directly to Tasks.
6. Protected operations enforce RBAC server-side.
7. Material writes produce versioned domain events.
8. AI-generated state requires provenance.
9. Human confirmation does not bypass target-module permissions.
10. Correlation IDs trace truthful request and processing contexts; complete business journeys may span multiple correlation IDs and are reconstructed through durable provenance, aggregate identity, causation, and audit projection.
11. Retryable commands must be idempotent where required.
12. Changes affecting contracts or architecture are recorded in `CHANGELOG.md`.
13. Permission checks use permission codes rather than hard-coded role names.
14. The authenticated actor comes from `RequestContext.actorUserId`.
15. Read-model aggregation does not transfer authoritative ownership between modules.

---

## Acceptance Scenario

Given an authorised project member posts:

> Daniel, please finalise the syllabus by Friday.

Cadence shall:

1. Store the human message and version.
2. Emit `MessageCreated.v1`.
3. Create an AI run.
4. Create a pending task proposal.
5. Allow an authorised human to review the proposal.
6. Revalidate `agent.approve`.
7. Revalidate `task.create`.
8. Revalidate `task.assign` when an assignee is specified.
9. Create one authoritative task.
10. Record provenance to the originating proposal/message.
11. Emit `TaskCreated.v1`.
12. Make the task visible through `GET /me/tasks`.
13. Reconstruct the complete business journey across one or more truthful correlation IDs without rewriting request history.

## Project Workspace Read-Model Calculations

The following rules define the VS001-03 read model.

### My Tasks —Pending

Count tasks where:

```text
project_id = requested project
assigned_to = logged-in Cadence user
status IN (open, in_progress)
```

Conceptually:

```sql
project_id = project
AND assigned_to = current_user
AND status IN ('open', 'in_progress')
```

---

### My Tasks —Overdue

Count tasks where:

```text
project_id = requested project
assigned_to = logged-in Cadence user
status IN (open, in_progress)
due_date IS NOT NULL
due_date < current time/date
```

Conceptually:

```sql
project_id = project
AND assigned_to = current_user
AND status IN ('open', 'in_progress')
AND due_date IS NOT NULL
AND due_date < now
```

---

### Blockers

Count active blockers where:

```text
project_id = requested project
status IN (open, monitoring)
```

Resolved blockers are not counted.

---

### Next Milestone

Select the earliest incomplete milestone:

```text
project_id = requested project
status != completed
target_date IS NOT NULL
ORDER BY target_date ASC
LIMIT 1
```

If no qualifying milestone exists:

```text
next_milestone = null
```

---

### Alerts

Return alerts where:

```text
project_id = requested project

AND

(
  user_id IS NULL
  OR user_id = logged-in Cadence user
)

AND dismissed_at IS NULL

AND starts_at <= now

AND

(
  expires_at IS NULL
  OR expires_at > now
)
```

A null:

```text
user_id
```

represents a project-wide alert.

A populated `user_id` represents a user-specific alert.

```text

```


## Authorization

```text

  ->

message.create
```

```text

```

---

## Defence in Depth

The Discussion PostgreSQL function performs a second `message.create` permission check immediately before persistence.

The function uses:

```text
SECURITY DEFINER
search_path = public, pg_temp
```

Execution is revoked from:

```text
public
anon
authenticated
```

and granted to:

```text
service_role
```

Browser clients must not invoke this persistence function directly.

## Per-Consumer Deliveries

VS001-05 adds:

```text
public.domain_event_deliveries
```

A delivery is identified by:

```text

+

```

This allows multiple consumers to process the same domain event independently.

For example:

```text

        |
        +--> Team Agent

        |

```

One consumer may succeed, fail, or retry without changing another consumer's delivery state.


---

## Atomic Claiming

Delivery claiming uses PostgreSQL:

```text
FOR UPDATE OF d SKIP LOCKED
```

through:

```text
public.claim_domain_event_delivery(...)
```

This allows concurrent workers to safely claim different available deliveries.

The default processing lease is:

```text
900 seconds
```

A successful claim receives a unique claim token.

---

## Claim Token and Lease Safety

Claim tokens prevent stale workers from completing or failing a delivery after another worker has reclaimed it.

Conceptually:

```text
Worker A claims delivery with token A
  ->
Worker A stalls
  ->
lease expires
  ->
Worker B reclaims delivery with token B
  ->
Worker A later tries to complete with token A
  ->
completion rejected
```

Expired processing leases may be reclaimed.

## Objective

Implement the human-review boundary for a non-authoritative pending Team Agent task proposal:

```text
pending proposal
  ->
authorised human review
  ->
agent.approve
  ->

```

---

## API

Authenticated endpoint:

```text

```

```text

```

The authenticated reviewer is always taken from:

```text
RequestContext.actorUserId
```

Client-supplied reviewer identity is not accepted as authority.

---

## Authorization

Proposal review requires:

```text
agent.approve
```

The permission is checked through project-scoped RBAC using permission codes rather than hard-coded role names.

Authorization is enforced twice:

```text
TeamAgentService
  -> agent.approve
  -> TeamAgentRepository
  -> PostgreSQL review RPC
  -> agent.approve revalidation
```

The database recheck provides defence in depth if access changes between application authorization and persistence.

---

## Review State Model

The original AI-generated proposal remains in:

```text
ai_proposals.payload
```

The final human-reviewed proposal is stored in:

```text
ai_proposals.reviewed_payload
```

State rules:

```text
pending
  payload = original AI proposal
  reviewed_payload = null

confirmed
  payload = original AI proposal
  reviewed_payload = copy of original AI proposal

edited
  payload = original AI proposal
  reviewed_payload = final human-reviewed proposal

rejected
  payload = original AI proposal
  reviewed_payload = null
```

This preserves AI provenance instead of overwriting the original proposal.

---

## Confirm

Confirm accepts the AI proposal as-is:

```text
pending
  ->
confirmed
```

The persistence operation copies the original AI payload into `reviewed_payload`, records the human reviewer and timestamp, and emits:

```text
AIProposalConfirmed.v1
```

Confirm does not create a Task in VS001-06.

---

## Edit

Edit stores a separate reviewed proposal:

```text
pending
  ->
edited
```

Human-reviewed values may change task proposal fields such as title and description.

The following provenance fields are immutable during review:

```text
source_message_id
source_message_version_id
```

The original AI `payload` remains unchanged.

Successful edit emits:

```text
AIProposalEdited.v1
```

---

## Reject

Reject transitions:

```text
pending
  ->
rejected
```

A rejected proposal keeps:

```text
reviewed_payload = null
```

while recording the reviewer and review timestamp.

Successful rejection emits:

```text
AIProposalRejected.v1
```

A rejected proposal cannot create a Task through VS001-06.

# VS001-07 - Authoritative Task Creation

Status: Complete

## Objective

Convert a human-reviewed Team Agent task proposal into an authoritative Task while preserving module ownership, RBAC, provenance, idempotency, correlation, and causation.

Implemented path:

```text
confirmed / edited proposal
  ->
TeamAgentTaskMaterializationService
  ->
TasksService
  ->
task.create
  ->
task.assign when required
  ->
TasksRepository
  ->
Tasks-owned persistence
  ->
authoritative Task
  ->
TaskCreated.v1
```

Team Agent never writes directly to `public.tasks`.

---

## Architectural Boundary

The authoritative dependency direction is:

```text
Team Agent
  ->
TasksService
  ->
TasksRepository
  ->
SupabaseTasksRepository
  ->
public.create_authoritative_task(...)
  ->
public.tasks
```

The Team Agent module must not depend directly on:

```text
TasksRepository
SupabaseTasksRepository
public.tasks
```

A source scan after implementation returned no prohibited Team Agent dependency.

---

## Authorization

Authoritative Task creation requires:

```text
task.create
```

When `assigned_to` is non-null, the actor must also have:

```text
task.assign
```

These permissions are independent from:

```text
agent.approve
```

Human proposal review therefore does not grant implicit authority to create or assign Tasks.

`TasksService` evaluates project access and the required permission codes. The Tasks-owned PostgreSQL persistence function repeats the authorization checks for defence in depth.

The authoritative creator comes from:

```text
RequestContext.actorUserId
```

and is persisted with:

```text
created_by_type = human
```

```text

```

```text
ai_proposals.reviewed_payload
```

rather than directly from the original AI-generated `payload`.

The following states cannot create an authoritative Task:

```text
pending
rejected
expired
```

This preserves the original AI proposal while ensuring that human-reviewed values become authoritative.

# VS001-09 — Complete Audit Reconstruction

Status: Complete

## Objective

Complete the audit portion of VS-001 by reconstructing the full:

```text
Discussion
  ->
MessageCreated.v1
  ->
Team Agent task proposal
  ->
Human review
  ->
Authoritative Task
```

business journey.

The implementation preserves truthful request-level correlations rather than manufacturing one correlation ID across separate human HTTP interactions.

---

## Architectural Decision

Earlier VS-001 wording assumed that the complete journey should be reconstructed through one correlation ID.

Live implementation and verification demonstrated that this is not the correct long-term model for a workflow that spans multiple requests.

Cadence now distinguishes:

```text
Request correlation
    = one technical request / processing context

Business reconstruction
    = one logical business journey assembled from durable relationships
```

A business journey may therefore contain multiple correlation IDs.

The Audit module reconstructs that journey through:

```text
provenance
+ aggregate identity
+ causation
+ audit projection
+ correlation metadata
```

Original correlation IDs remain unchanged.

---

## Audit Projection

VS001-09 adds the independent consumer:

```text
audit.domain-events.v1
```

for:

```text
MessageCreated.v1
AIProposalCreated.v1
AIProposalConfirmed.v1
AIProposalEdited.v1
AIProposalRejected.v1
TaskCreated.v1
```

Projection is performed through:

```text
public.project_domain_event_to_audit(event_id)
```

The function projects material domain events into the append-only:

```text
public.audit_events
```

store.

`audit_events.event_id` is used as the idempotency key.

A repeated delivery therefore becomes a harmless no-op rather than creating duplicate Audit records.

The original domain-event occurrence time is preserved as the Audit event creation time.

---

## Historical Audit Backfill

New domain-event subscriptions do not automatically replay historical events.

VS001-09 therefore explicitly backfills existing supported VS-001 domain events into `audit_events`.

## Worker Integration

The worker now processes Audit and Team Agent deliveries as independent consumers.

Conceptually:

```text

    |
    +-> one Team Agent delivery
```

A failure in one consumer does not erase or invalidate another consumer's delivery state.

This preserves module independence and allows Audit recording to remain decoupled from Team Agent processing.

Successful Task creation preserves causation to the confirmed or edited proposal-review event.

This allows Audit to cross truthful request-correlation boundaries without rewriting history.
