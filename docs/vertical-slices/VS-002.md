# Cadence VS-002 — Project Membership & Collaboration Contract

**Version:** 0.2
**Status:** Frozen
**Vertical Slice:** VS-002
**Predecessor:** VS-001 — Complete
**Primary Capability:** Multi-user Project Membership, Roles, Access and Collaboration Governance

---

# 1. Objective

VS-002 proves that multiple authorised users can securely participate in the same Cadence project regardless of whether they are internal or external participants.

Cadence shall support:

* controlled project membership;
* project-level roles;
* internal and external participants;
* time-bounded project access;
* controlled succession of key project responsibilities;
* read-only oversight and audit roles;
* stable historical identity;
* permission enforcement;
* complete auditability.

VS-002 establishes the people-and-access foundation required for future Cadence capabilities without implementing those future capabilities prematurely.

---

# 2. Business Outcome

After completion of VS-002:

1. Multiple authorised users can participate in the same project.
2. One person can participate in multiple projects.
3. Project participation is independent of department, company or organisational affiliation.
4. Internal and external identities can participate in projects.
5. An external participant may serve as Project Manager where authorised.
6. Project Managers and Project Owners can manage ordinary membership.
7. Sponsor, Project Owner and Project Manager assignments can change without losing history.
8. Observer and Auditor roles provide controlled read-only access.
9. Membership may be open-ended or time-bounded.
10. Leaving an organisation terminates active access without destroying historical attribution.
11. A returning person can be linked to a new login identity while preserving historical records.
12. Historical permissions are never automatically restored merely because the person returns.
13. Unauthorised users cannot access project information simply because they belong to the same department or organisation.
14. Membership, role and responsibility changes are auditable.
15. VS-001 behaviour continues to operate correctly.

---

# 3. Core Architectural Principles

These are Cadence invariants and shall not be violated by VS-002 implementation.

## 3.1 Person, Authentication and Membership Are Different Concepts

Cadence shall distinguish:

```text
PERSON
  │
  ├── Authentication Identity
  │
  ├── Organisational Affiliation
  │
  └── Project Membership
```

A person's email address or login account shall not be treated as their permanent Cadence identity.

---

## 3.2 Authentication Is Not Project Authorisation

Authentication establishes:

> Who is this person?

Project membership and permissions establish:

> What is this person allowed to do in this project?

Changing authentication providers must not require redesign of project-role or permission logic.

---

## 3.3 Organisational Affiliation Does Not Determine Project Authority

An internal employee is not automatically more powerful than an external participant.

Valid combinations include:

```text
INTERNAL + PROJECT_MANAGER
EXTERNAL + PROJECT_MANAGER

INTERNAL + PROJECT_MEMBER
EXTERNAL + PROJECT_MEMBER

INTERNAL + PROJECT_OBSERVER
EXTERNAL + PROJECT_OBSERVER

INTERNAL + PROJECT_AUDITOR
EXTERNAL + PROJECT_AUDITOR
```

Project authority is determined by project permissions and roles.

---

## 3.4 Department or Organisational Membership Does Not Grant Project Access

Being part of the organisational unit that owns a project does not automatically grant access to project content.

Access requires an authorised project membership or another explicitly authorised access mechanism.

---

## 3.5 Management Reporting Access Does Not Equal Project Content Access

Future department, enterprise, legal-entity, regional or group dashboards may display authorised management information without granting access to confidential project content.

```text
Portfolio visibility
        ≠
Project-content visibility
```

---

## 3.6 Administrative Authority Does Not Automatically Grant Project Reading Rights

A technical or platform administrator does not automatically become a project member or gain ordinary access to confidential project content.

Future exceptional access mechanisms must be separately controlled and auditable.

---

## 3.7 Historical Project Records Must Not Be Overwritten

Membership termination and role transfer shall preserve previous records.

Cadence must remain capable of answering:

> Who held this role or membership at a particular point in the project's history?

---

## 3.8 No Hard Deletion of Membership History

Removing a person from a project terminates active access.

It does not delete:

* historical membership;
* role history;
* task attribution;
* discussion attribution;
* approvals;
* decisions;
* audit history.

---

## 3.9 AI Cannot Extend Access Rights

Future AI capabilities may access only information the requesting user is already authorised to access.

If a user cannot read project information directly, AI must not reveal it on the user's behalf.

---

# 4. Stable Cadence Person Identity

Cadence shall maintain a stable person identity independent of email address and authentication account.

Conceptually:

```text
Cadence Person
PER-00127
Sarah Tan

├── Authentication Identity 1
│   sarah.tan@organisation.example
│   Status: DISABLED
│
└── Authentication Identity 2
    s.tan@organisation.example
    Status: ACTIVE
```

Historical work remains associated with the stable Cadence Person.

It shall not be reassigned merely because a person's email address changes.

---

# 5. Authentication Identity

An authentication identity represents a mechanism through which a Cadence Person authenticates.

Conceptually:

```text
AuthenticationIdentity

person_id
provider
provider_subject_id
login_identifier
valid_from
valid_to
status
```

VS-002 must remain compatible with:

* current local authentication;
* future Microsoft Entra ID;
* future external/B2B identities;
* replacement authentication identities.

Authentication implementation must not become the source of project permission truth.

---

# 6. Returning Person / Rehire Scenario

A person may:

1. leave the organisation;
2. have their enterprise authentication account disabled;
3. later rejoin;
4. receive a different enterprise login or email address.

Where a trusted identity-management process determines that the returning identity belongs to the same person, the new authentication identity may be linked to the existing Cadence Person.

Example:

```text
PERSON
Sarah Tan
PER-00127

Employment period 1
Authentication:
sarah.tan@old.example
Status: Disabled

Employment period 2
Authentication:
s.tan@new.example
Status: Active
```

Historical project attribution remains associated with `PER-00127`.

---

# 7. Identity Relinking Must Not Restore Project Access

Linking a new authentication identity to an existing Cadence Person shall **not automatically restore historical memberships or permissions**.

Example:

```text
Historical membership:
Project Alpha
PROJECT_MEMBER
Jan 2027 – Jun 2028
ENDED

Sarah rejoins organisation:
Aug 2029

Project access:
NONE
```

If Sarah is required to participate again, an authorised person creates a new project membership.

```text
Membership #1
Jan 2027 – Jun 2028
ENDED

Membership #2
Sep 2029 – Present
ACTIVE
```

Both periods remain historically distinct.

---

# 8. Identity Matching Safety

Cadence must never assume that two authentication accounts represent the same person merely because:

* names match;
* email addresses are similar;
* usernames resemble one another.

Identity relinking must use a trusted mechanism such as:

* enterprise identity lifecycle information;
* authorised administrator confirmation;
* trusted identity-provider identifier;
* approved organisational identifier.

Incorrect identity merging is a security issue.

---

# 9. Identity Affiliation

A Cadence Person may have an organisational affiliation classification relevant to their current relationship with the organisation.

Initial classifications:

```text
INTERNAL
EXTERNAL
```

This classification does not determine project permissions.

A person's affiliation may change over time.

For example:

```text
Sarah Tan

2026–2028
Affiliation: INTERNAL

2029–
Affiliation: EXTERNAL
Organisation: ABC Consulting
```

Historical affiliation must remain understandable where relevant.

---

# 10. Project Roles

VS-002 establishes the following project roles:

| Role               | Purpose                                      |
| ------------------ | -------------------------------------------- |
| `PROJECT_SPONSOR`  | Executive sponsorship and governance         |
| `PROJECT_OWNER`    | Organisational accountability                |
| `PROJECT_MANAGER`  | Operational project management               |
| `PROJECT_MEMBER`   | Direct contribution to project delivery      |
| `PROJECT_OBSERVER` | Read-only oversight                          |
| `PROJECT_AUDITOR`  | Independent read-only assurance/audit access |

Roles shall not be tied to internal/external affiliation.

---

# 11. Project Membership and Role Assignment Are Separate Concepts

Cadence shall distinguish:

```text
PROJECT MEMBERSHIP
      │
      └── Authorised relationship with project
                │
                └── ROLE ASSIGNMENT
                     ├── Sponsor
                     ├── Owner
                     ├── Manager
                     ├── Member
                     ├── Observer
                     └── Auditor
```

Membership determines whether the person currently has an authorised relationship with the project.

Role assignment determines authority within that relationship.

---

# 12. Membership Duration

A project membership may be:

```text
OPEN-ENDED

or

TIME-BOUNDED
```

Membership shall support:

```text
effective_from
effective_to
status
granted_by
created_at
termination_reason
```

where applicable.

Persisted historical membership may record `granted_by = NULL` only when the
VS-001 source did not preserve grantor provenance. Null means unknown
historical provenance; it must not be filled with the member, an administrator,
a system Person, or another arbitrary identity. Every newly created VS-002
membership requires a real stable Person grantor.

---

# 13. Temporary Membership Is Not a Separate Role

Cadence shall not introduce:

```text
TEMPORARY_PROJECT_MEMBER
```

as a project role.

Temporary access is a property of membership duration.

Valid examples include:

```text
PROJECT_MEMBER
1 Sep – 30 Nov 2026

PROJECT_OBSERVER
1 Oct – 14 Oct 2026

PROJECT_AUDITOR
1 Nov – 30 Nov 2026
```

Role answers:

> What may this person do?

Membership duration answers:

> For how long may this person participate?

These concepts must remain independent.

---

# 14. Membership Expiry

When a time-bounded membership expires:

1. active project access ceases;
2. historical membership remains;
3. historical contributions remain attributed to the person;
4. ordinary active role assignments associated with the membership terminate where appropriate;
5. a membership-expiry domain event is emitted;
6. the expiry is recorded through Audit.

Expiry must never physically delete the membership record.

---

# 15. Expiry Responsibility Protection

Cadence must not allow automatic membership expiry to silently orphan protected project responsibilities.

Where an expiring member:

* holds a key responsibility;
* owns active Tasks responsibilities that cannot safely become unassigned;
* holds another protected project responsibility;

Cadence must identify the conflict before expiry according to applicable rules.

VS-002 does not implement temporary Sponsor, Owner or Project Manager delegation.

Temporary leadership/delegation remains future scope.

---

# 16. External Participants and Time-Bounded Access

Time-bounded membership should be encouraged for external participants when the expected participation period is known.

Example:

```text
David Lim
ABC Consulting

Affiliation:
EXTERNAL

Role:
PROJECT_MEMBER

Effective:
1 Sep 2026

Expires:
30 Nov 2026
```

External memberships do not have to be temporary.

Legitimate long-running external collaboration remains supported.

---

# 17. Role Assignment History

Project-role assignments must support historical validity.

Conceptually:

```text
ProjectRoleAssignment

project_id
membership_id
role
effective_from
effective_to
assigned_by
change_reason
created_at
```

The implementation may differ structurally, but the historical semantics must be retained.

---

# 18. Key Project Roles

The following are protected responsibility roles:

```text
PROJECT_SPONSOR
PROJECT_OWNER
PROJECT_MANAGER
```

Changing these assignments constitutes a **responsibility transfer**, not an ordinary membership edit.

---

# 19. Controlled Responsibility Transfer

A key-role transfer shall record:

* outgoing role holder;
* incoming role holder;
* role;
* effective date/time;
* person authorising or initiating transfer;
* reason;
* correlation information.

Example:

```text
PROJECT_MANAGER

David Lim
1 Sep 2026 – 15 Nov 2026

Mei Tan
16 Nov 2026 – Present
```

Historical assignments remain intact.

---

# 20. Atomic Role Transfer

Cadence must perform protected role transfer as one controlled business operation.

The implementation must not:

1. remove the old Project Manager;
2. leave the project temporarily without a Project Manager;
3. then separately create the replacement.

The operation must preserve valid project state throughout the transfer.

---

# 21. External Project Manager

VS-002 explicitly permits:

```text
Affiliation: EXTERNAL
Role: PROJECT_MANAGER
```

An external Project Manager receives the operational permissions associated with the role.

The project domain must not hard-code a restriction preventing external Project Managers.

Future organisational policy may impose additional rules without redesigning membership.

---

# 22. Project Ownership and Project Management Are Separate

Cadence shall distinguish:

```text
PROJECT_OWNER
Organisational accountability

PROJECT_MANAGER
Operational management
```

Example:

```text
Owning organisational unit:
IT

Project Owner:
Internal authorised person

Project Manager:
External consultant
```

An external Project Manager can therefore run an organisational project while internal accountability remains clear.

---

# 23. Project Sponsor

The Sponsor provides executive sponsorship or governance.

Changing the Sponsor must be historically recorded.

Sponsor transfer must not overwrite the previous Sponsor record.

---

# 24. Ordinary Membership Management

Authorised Project Managers and Project Owners may perform ordinary membership operations as permitted by the VS-002 permission model.

These include:

* viewing project members;
* adding an existing Cadence Person;
* assigning an ordinary project role;
* changing ordinary roles;
* removing ordinary members;
* reviewing current memberships.

Identity provisioning remains separate from project membership.

---

# 25. External Identity Provisioning Boundary

VS-002 supports membership for external Cadence identities.

The membership module must not depend on whether the external identity was provisioned through:

* local authentication;
* Microsoft Entra External ID/B2B;
* another future identity provider.

Invitation delivery and complete production external-account onboarding may be handled during later production authentication hardening.

---

# 26. Project Observer

`PROJECT_OBSERVER` provides controlled read-only project access.

Typical uses:

* management oversight;
* stakeholder monitoring;
* client representatives;
* staff requiring visibility without direct contribution;
* future project participants.

Observers shall not be counted as delivery-team resources in future project-team statistics.

---

# 27. Project Auditor

`PROJECT_AUDITOR` provides independent read-only assurance access.

The role is distinct from Observer because future Auditor functionality may include authorised access to:

* project audit history;
* previous project roles;
* approvals;
* historical project information;
* document revisions;
* membership changes;
* AI proposal/human-approval records.

Advanced Auditor interfaces remain future scope.

---

# 28. Read-Only Enforcement

Read-only permissions must be enforced by backend authorisation.

Hiding frontend controls is not security.

At minimum:

```text
PROJECT_OBSERVER

READ      ALLOWED
CREATE    DENIED
UPDATE    DENIED
DELETE    DENIED


PROJECT_AUDITOR

READ      ALLOWED
CREATE    DENIED
UPDATE    DENIED
DELETE    DENIED
```

Access to specialised audit information may be independently controlled.

---

# 29. Membership Removal

Removing a project member must:

1. terminate active membership;
2. terminate relevant active ordinary role assignments;
3. preserve historical membership;
4. preserve historical role assignments;
5. preserve attribution of past work;
6. revoke future project access;
7. generate domain events;
8. produce audit records.

A removed person must not disappear from historical project records.

---

# 30. Responsibility Guard

Cadence must prevent membership removal when doing so would create invalid project state.

At minimum:

* protected roles must be transferred before required membership removal;
* a Project Manager cannot be removed if this would leave the project without required operational leadership;
* a Project Owner cannot be removed where ownership would become invalid.

---

# 31. Task Responsibility Guard

The Project Membership capability shall use a published Tasks contract to determine whether removing a member would orphan active task responsibility.

Project Membership must not query Tasks persistence directly.

Where blocking responsibilities exist, member removal returns an explicit conflict.

Sophisticated reassignment UI remains outside VS-002.

---

# 32. Future Temporary Delegation

Acting appointments and delegated authority are recognised future requirements.

Example:

```text
Permanent Project Manager:
Sarah Tan

Acting Project Manager:
Mei Tan
1 Sep – 14 Sep
```

VS-002 does not implement temporary leadership delegation.

Its role-history design must not prevent this capability later.

---

# 33. Project Authorisation Contract

VS-002 shall establish a single project-authorisation interface for use by other modules.

Conceptually:

```text
canAccessProject(
  context,
  projectId
)

hasProjectPermission(
  context,
  projectId,
  permission
)

getEffectiveProjectRoles(
  personId,
  projectId
)
```

Other modules shall not independently interpret project-membership persistence.

# 35. API Capabilities

Exact route implementation may vary, but VS-002 must expose equivalent capabilities.

## 35.1 List Project Members

```text
GET /api/v1/projects/:projectId/members
```

Returns authorised membership information visible to the requesting person.

---

## 35.2 Add Project Member

```text
POST /api/v1/projects/:projectId/members
```

Conceptual request:

```json
{
  "person_id": "...",
  "role": "PROJECT_MEMBER",
  "effective_from": "...",
  "effective_to": null
}
```

---

## 35.3 Add Time-Bounded Project Member

Same capability with an expiry:

```json
{
  "person_id": "...",
  "role": "PROJECT_MEMBER",
  "effective_from": "2026-09-01T00:00:00Z",
  "effective_to": "2026-11-30T23:59:59Z"
}
```

---

## 35.4 Change Ordinary Role

```text
PATCH /api/v1/projects/:projectId/members/:membershipId
```

This endpoint shall not be used to bypass protected key-role transfer.

---

## 35.5 Remove Member

```text
DELETE /api/v1/projects/:projectId/members/:membershipId
```

Removal is logical/temporal rather than destructive deletion.

---

## 35.6 Transfer Key Role

```text
POST /api/v1/projects/:projectId/role-transfers
```

Conceptual request:

```json
{
  "role": "PROJECT_MANAGER",
  "new_membership_id": "...",
  "effective_at": "...",
  "reason": "..."
}
```

# 38. Audit Requirements

Audit remains responsible for audit storage and query behaviour.

Project Membership emits events and must not write Audit persistence directly.

Audit records must provide enough information to establish:

```text
Who performed the action?
Who was affected?
Which project was affected?
What changed?
What was the previous state?
What became the new state?
When did it take effect?
Why was it changed?
What request/correlation caused it?
```

Audit history remains after membership termination or authentication-account deactivation.

---

# 39. Module Boundaries

## Identity / Authentication

Owns:

* stable Cadence Person;
* authentication identities;
* authentication-provider mapping;
* enabled/disabled account status;
* internal/external affiliation;
* trusted relinking of returning users.

Does not own project membership.

---

## Projects

Owns:

* project identity;
* project existence;
* project lifecycle information belonging to Projects;
* future organisational ownership reference.

Does not interpret membership permissions internally.

---

## Project Membership / Access

Owns:

* project membership lifecycle;
* membership duration;
* project-role assignments;
* protected role transfer;
* project-level access decisions;
* membership queries;
* membership-related domain events.

---

## Tasks

Owns:

* task state;
* task assignment;
* task lifecycle.

Exposes an interface required to determine whether membership termination would orphan active task responsibility.

---

## Discussion

Owns discussion content and behaviour.

Uses Project Authorisation to determine whether a user may read or contribute.

Must not query membership persistence directly.

---

## Audit

Owns:

* audit persistence;
* audit read models;
* audit queries.

Consumes relevant project-membership and role events.

---

# 46. Forward-Compatible Architectural Allowances

VS-002 shall not assume:

```text
organisation = one department

organisational hierarchy = fixed depth

project manager = internal employee

one person = one email forever

authentication account = person

historical membership = current permission

administrator = universal project reader

department membership = project membership

```

Future organisational structures may include:

```text
Group
→ Legal Entity
→ Region
→ Division
→ Department
→ Business Unit
```

VS-002 does not implement this hierarchy.

It merely avoids architectural assumptions that would make it impossible.

# 47. Acceptance Criteria

## AC-01 — Multi-User Project

Two or more authorised Cadence Persons can access the same project.

## AC-02 — Multi-Project Membership

One Cadence Person can participate in multiple projects.

## AC-03 — Project Isolation

An authenticated person without authorised project access is denied access to protected project content.

## AC-04 — Internal Participant

An internal person can participate in a project.

## AC-05 — External Participant

An external person can participate in a project.

## AC-06 — External Project Manager

An external person can hold `PROJECT_MANAGER`.

## AC-07 — Membership Management

Authorised Project Manager/Owner can add and remove ordinary project members.

## AC-08 — Member Listing

Authorised project participants can view permitted project membership information.

## AC-09 — Observer Read-Only

Observer can read authorised project content but cannot mutate project state.

## AC-10 — Auditor Read-Only

Auditor cannot mutate project state.

## AC-11 — Protected Role Transfer

Sponsor, Owner and Project Manager assignments can change without destroying previous role history.

## AC-12 — Responsibility Guard

Cadence prevents removal that would leave an invalid protected-role state.

## AC-13 — Task Responsibility Guard

Cadence prevents removal that would improperly orphan active Tasks responsibilities.

## AC-14 — Historical Membership Preservation

Removed members remain correctly represented in historical information.

## AC-15 — Audit

Membership additions, removals, expiry and role changes generate auditable records.

## AC-16 — Backend Enforcement

Direct API calls cannot bypass access restrictions hidden by the frontend.

## AC-17 — VS-001 Regression

VS-001 discussion → proposal → review → task → audit continues functioning correctly.

## AC-18 — Module Isolation

Discussion, Tasks and other modules use published Project Authorisation contracts rather than direct membership persistence access.

## AC-19 — Time-Bounded Membership

Authorised users can create an ordinary membership with an expiry date.

## AC-20 — Membership Expiry

Expired membership loses active project access while historical records remain.

## AC-21 — Expiry Audit

Automatic membership expiry generates an auditable event.

## AC-22 — Role/Duration Independence

Membership duration does not change the permission meaning of a role.

## AC-23 — Stable Person Identity

Historical project attribution is associated with a stable Cadence Person rather than email address.

## AC-24 — Authentication Identity Replacement

A new trusted authentication identity can be linked to the same Cadence Person without altering historical attribution.

## AC-25 — No Automatic Permission Restoration

Linking a returning person's new authentication identity does not restore previous project membership.

## AC-26 — Returning Person Rejoins Project

### VS002-02 implementation record

The forward-only migration
`20260820000100_vs002_membership_persistence.sql` introduces:

* `public.persons` as the stable human identity anchor;
* `public.authentication_identities` as replaceable provider/subject/login
  records with independent validity and status;
* `public.organisational_affiliations` as independent time-varying
  `INTERNAL`/`EXTERNAL` history;
* new stable-Person, period, lifecycle, grantor, creation, and termination
  fields on the existing `public.project_memberships`; and
* `public.project_role_assignments` as separate frozen-role history.

The migration evolves the VS-001 membership table rather than creating a
second authority. Existing `user_id`, `role_id`, lowercase status, and
`joined_at` fields remain available to current RBAC and RLS functions.
`effective_from` and frozen `membership_status` are generated compatibility
projections, so current rows retain their original meanings while the new
repository reads the VS-002 model.

#### Deterministic identity bridge

Every existing `public.users.id` becomes the initial `public.persons.id`, and
`public.users.person_id` records that exact relationship. This preserves all
existing actor identifiers and historical foreign keys. The migration does
not match or merge on name, display name, username, email, organisation, or
approximate similarity.

Existing authentication rows are backfilled only when the working
`auth_user_id` subject exists. The existing `identity_provider` and exact
`auth_user_id` become provider/subject data; email is copied only as a mutable
login identifier. `users.created_at` supplies the Cadence mapping start.
Disabled rows retain `DISABLED` with null `valid_to` because VS-001 has no
dedicated authentication-disable timestamp. Rows without an explicit subject
are not guessed. No organisational affiliation is inferred from VS-001 data.

#### Membership and role backfill

Existing memberships map to Person through the exact `user_id` FK.
`joined_at` supplies the historical effective start and missing creation time.
For existing inactive rows, `updated_at` is the only available recorded
lifecycle boundary and supplies `effective_to`; a one-microsecond floor is
used only when necessary to preserve a positive interval. Nullable
`created_by` maps to a stable grantor only through its exact user FK. When the
source is null, `granted_by_person_id` remains null without substitution.

Existing VS-001 role IDs are not reinterpreted as frozen roles.
`PROJECT_LEAD`, `CONTRIBUTOR`, `REVIEWER`, and `VIEWER` do not have exact
one-to-one semantic equivalents in the frozen vocabulary. Their current IDs,
permissions, and access remain authoritative for VS-001, and an explicit
approved data decision is required before later runtime integration.

#### Persistence ownership and operations

Identity publishes `IdentityPersistenceRepository` and owns Person,
Authentication Identity, and affiliation persistence. Project Membership
publishes `ProjectMembershipRepository` and owns membership and role-assignment
persistence. Straightforward Supabase adapters provide foundational create/read
operations only. Projects and RBAC do not own or directly write the new state.

Persisted `ProjectMembership` uses `grantedBy: string | null` to represent
truthful VS-001 history. `CreateProjectMembershipInput` requires
`grantedBy: string`, and Person-only database rows require a non-null
`granted_by_person_id`. Legacy rows with non-null compatibility `user_id`
remain valid when their original `created_by` was null.

New VS-002 membership persistence leaves compatibility `user_id` and `role_id`
null. Persistence alone therefore cannot grant access through the existing
VS-001 RBAC path. Existing rows retain those fields and retain their working
access.

#### Constraints, indexes, and security

Database constraints enforce provider-subject uniqueness, exact identity and
affiliation status vocabularies, positive bounded periods, `ENDED` membership
with an end, the frozen six-role vocabulary, foreign keys, and role-assignment
membership/project consistency. The compatibility bridge also requires a
legacy `user_id` to reference the same Person and to be paired with a legacy
`role_id`, preventing malformed compatibility rows from becoming an accidental
VS-001 access path. It also requires a grantor for Person-only membership rows
without invalidating legacy rows whose grantor was unavailable. Indexes support
later identity-validity, affiliation-
history, project/Person membership, and role-history lookups.

Hard deletion is prevented for Person, authentication identity, affiliation,
membership, and role-assignment history. No trigger implements role transfer,
expiry, or future authorization policy.

RLS is enabled on new tables. They have no anonymous/authenticated browser
grants in this checkpoint and receive explicit server-side service-role
privileges. The existing authenticated
`memberships_select_project_member` policy is dropped and recreated under the
same name with the existing `is_project_member(project_id)` check plus non-null
legacy `user_id` and `role_id` predicates. Authenticated direct reads therefore
retain the VS-001 compatibility path but cannot expose Person-only VS-002 rows.
Service-role repository access remains available. This is a temporary defensive
compatibility restriction; VS002-03 remains responsible for Project
Authorisation.

The API typecheck and 93-test suite pass. Thirteen focused VS002-02 tests cover
repository mapping, multiple authentication identities for one Person,
identity/membership separation, affiliation/role separation, external Project
Manager persistence, open-ended/time-bounded membership, independent role
periods, deterministic backfill structure, frozen-role enforcement, server-only
identity data, truthful null grantor mapping, required new grantors, database
constraint structure, and restricted authenticated compatibility reads.

The migration is not applied remotely by this checkpoint implementation.
After human review, use `supabase db push --dry-run`, then the controlled push,

The repository uses forward-only migrations and provides no destructive down

### VS002-03 implementation record

`ProjectAuthorisationService` is the single published decision boundary for:

```text
canAccessProject(context, projectId)
hasProjectPermission(context, projectId, permission)
```
