# VS003 — Durable Discussion Read and Return Path

**Status:** Contract frozen; implementation not begun
**Version:** 1.0
**Milestone:** M1 — Controlled Pilot
**Predecessors:** VS-001 Complete; VS-002 Complete

## Objective

Provide the smallest user-facing capability required for a controlled pilot to
recover shared Discussion context after entering, reloading, leaving, or
returning to a configured project.

An authorised user must be able to:

```text
enter configured project
  ->
load persisted Discussion
  ->
post
  ->
reload or leave
  ->
return and recover context
  ->
explicitly refresh
  ->
see another authorised user's committed message
```

Realtime and automatic push convergence are explicitly outside this slice.

## Problem statement

VS-001 proves authenticated Discussion creation, immutable version persistence,
and asynchronous `MessageCreated.v1` processing. The current browser does not
load persisted messages: it keeps message state for the current browser
session, and the API exposes no project-message list/read route.

Without a read/return path, a second user or returning user cannot recover the
shared project context required by M1.

## Scope

### API and module contract

- Add an authenticated project-scoped Discussion list/read contract through the
  Discussion module.
- Add `GET /api/v1/projects/:projectId/messages` or the equivalent published
  route agreed by the existing API conventions.
- Enforce project access through the canonical
  `ProjectAuthorisationService` and permission codes.
- Return current committed message versions in deterministic order.
- Return the author identity/type and committed timestamp needed for pilot
  collaboration.
- Preserve the standard response, request-ID, and correlation-ID envelope.
- Define empty, loading, failure, and retry behavior at the boundary.

### Browser behavior

- Load messages when entering the configured project workspace.
- Restore messages after browser reload and after leaving and returning.
- Provide explicit manual refresh.
- Provide a visible retry path for read failure.
- Show sufficient author and time information to distinguish messages from
  multiple users.
- Keep posting through the existing authenticated API command.

### Security and integrity

- Re-evaluate authorization at the server read boundary.
- Preserve project isolation and concealment/denial semantics.
- Allow authorised read-only Observer and Auditor scenarios to read according
  to their permissions, while preserving their inability to post.
- Keep browser business data API-only; no direct browser business-table access.
- Preserve RLS and service-role boundaries as defence in depth.
- Preserve VS-001 and VS-002 frozen behavior.

## Security boundaries

The implementation must preserve:

- `ProjectAuthorisationService` as the project authorization boundary;
- membership-based project isolation;
- permission-code, server-authoritative access decisions;
- Observer/Auditor read-only behavior;
- API-only browser access to business data;
- no service-role key in the browser;
- RLS defense in depth;
- module ownership and no direct cross-module persistence access; and
- all frozen VS-001/VS-002 authentication, authorization, event, provenance,
  and audit behavior.

Reading a message does not authorize a user to post, edit, review proposals,
or mutate Tasks. Those permissions remain independently enforced.

## Approved acceptance boundary

1. An authenticated authorised Member, Owner, Manager, or Sponsor can load the
   configured project’s persisted Discussion.
2. An authorised Observer or Auditor can read where the existing permission
   model grants Discussion read access, but cannot post through the existing
   `message.create` boundary.
3. A non-member cannot read another project’s messages; existing concealment or
   denial semantics remain intact.
4. Messages are project-isolated and returned in deterministic order.
5. The response identifies the current committed version, author/type, and
   committed time required for pilot use.
6. Entering the workspace performs an initial read.
7. Browser reload restores persisted messages.
8. Leaving and returning restores the same persisted context.
9. Explicit refresh causes a second authorised browser session to see a first
   user’s committed message.
10. Empty, loading, error, and retry states are visible and usable.
11. Existing POST behavior remains intact, including its validation,
    authorization, immutable version, and atomic event behavior.
12. Existing Team Agent and Audit processing remains intact.
13. No browser business-table access is introduced.
14. C08.1 and C08.2 are eligible for closure only if all implementation and
    runtime evidence passes.
15. C08.3 receives only the deterministic manual-refresh/shared-visibility
    advancement in this slice; realtime/automatic convergence remains due M2.
16. C08.4 remains delivered and regression protected.
17. INIT-AC-03 is eligible for closure only if its complete acceptance
    evidence passes; the contract itself does not close it.
