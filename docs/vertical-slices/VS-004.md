# VS-004 - Controlled Pilot Bootstrap and Access

**Status:** Contract Freeze (VS004-01); implementation not started
**Version:** 1.0
**Milestone:** M1 - Controlled Pilot
**Predecessors:** VS-001 Complete; VS-002 Complete; VS-003 merged at `88cf79d`

## 1. Purpose

VS-004 defines a repeatable, controlled operator procedure for preparing the
M1 pilot users, authentication identities, stable Persons, Cadence Users, one
real project, memberships, roles, and access decisions.

The procedure prepares an already governed Cadence environment for a small
internal pilot. It is an operator-assisted M1 capability, not a replacement
for the M2 self-service project-creation and onboarding outcome.

No real pilot content or live pilot user operation may begin until the M1
Pilot Activation Gate in `docs/milestones/M1_CONTROLLED_PILOT.md` passes.

## 2. Scope

The default pilot assumption is:

- 5-10 named internal users;
- one real project;
- one distinct default Owner, Manager, Sponsor, and ordinary Member
  assignment, with enough named users to rehearse their access behavior; and
- optional Observer and Auditor scenarios where they add useful evidence.

VS-004 covers the controlled preparation and verification of that topology.
It covers both first preparation and a second successful run against the same
intended state.

## 3. Explicit non-scope

VS-004 does not deliver or close:

- M2 self-service project creation, project discovery, navigation, or normal
  member onboarding;
- the full C01 outcome or C01.2 atomic project/health initialization outcome;
- Entra SSO, MFA, enterprise account lifecycle, or production identity
  operations (C06.4 and C06.5 remain on their governed path);
- external participation or external Project Manager onboarding;
- deployment hosting, stable deployment targets, or worker scheduling (VS005);
- backup technology, restore proof, recovery, support ownership, or incident
  procedure (VS006);
- a new authorization model, role vocabulary, membership persistence path, or
  browser business-data path;
- direct ad hoc SQL as a normal operator procedure;
- destructive repair, historical rewrite, hard deletion, truncation, or
  migration solely to support bootstrap; or
- reopening, amending, or weakening VS-001 or VS-002.

These exclusions change sequence only. They do not remove or move any
governed commitment beyond M3.

## 6. Operator-assisted bootstrap boundary

The operator procedure is a server-side, controlled administrative operation.
It may prepare empty accounts, Persons, a project, and memberships before the
Pilot Activation Gate, but it must not become a browser-visible self-service
creation flow.

VS004 defines a narrowly controlled bootstrap-only administrative authority.
This authority exists only for the server-side/operator bootstrap command. It
requires a validated environment and target plus protected administrative and
provider credentials. Each run records a named operator/authorising stable
Person and a correlation/run ID. It may create the initial empty project and
establish its first governed access state before project-scoped authority
exists. It is not exposed through the browser or the normal runtime API, does
not grant the operator universal application project access, and does not
replace `ProjectAuthorisationService` for any normal application request after
bootstrap.

The bootstrap coordinator is orchestration only. It must use published,
module-owned contracts for:

- authentication-provider account preparation;
- Identity-owned Person, Cadence User, authentication-identity, and optional
  affiliation preparation;
- Projects-owned project and project-state preparation; and
- Project Membership-owned canonical admission, ordinary-role change, and
  protected-role appointment/transfer.

Where no suitable published creation/preparation contract currently exists,
VS004 may add a narrow server-side, bootstrap-only application contract inside
the owning Identity or Projects module, but only as necessary for pilot
preparation. Such a contract must remain inside that module, preserve
persistence ownership, stay out of browser routes and self-service flows,
introduce no second authorization model, close no M2 self-service outcome,
and remain subject to the VS004 preflight, idempotency, and provenance rules.
The coordinator itself must never directly mutate another module's tables.

The coordinator must not interpret role names as permission authority, mutate
another module's tables, call another module's persistence directly, or
expose a service-role credential to a browser.

An operator run must have a named operator/authorizing stable Person, a
declared target environment, a declared pilot manifest, and a run/correlation
identifier. Operator provenance is not a substitute for project permission;
the application still evaluates every pilot user's project authority through
`ProjectAuthorisationService`.

## 7. Pilot user requirements

Each pilot user must have:

- a unique manifest key and unique intended login identifier;
- a unique stable Person reference or an explicitly resolved existing Person;
- a Cadence User mapped to that Person;
- one active authentication identity mapped to the same Person and provider
  subject used by the authentication provider;
- an active Cadence User status for pilot login; and
- an explicit intended project role or role scenario.

The default manifest contains 5-10 named internal users and one project. The
default Owner, Manager, Sponsor, and ordinary Member are distinct named
Persons so the pilot exercises distinct authority paths. Any deliberate role
overlap must be explicit in the manifest and verified as a separate scenario;
it must not be inferred from email, display name, department, or platform
administrator status.

Passwords and provider secrets are supplied through protected environment
configuration or the provider's controlled operator interface. They must not
be stored in the manifest, logs, Git, browser bundles, or this contract.

## 8. Authentication identity -> Person -> Cadence User relationship

The stable authorization identity is the Cadence Person. Authentication proves
who authenticated; it does not grant project access.

The operator must verify both parts of the current compatibility relationship:

```text
auth.users.id / provider subject
  -> authentication_identities.provider_subject_id
  -> authentication_identities.person_id
  -> persons.id

auth.users.id
  -> users.auth_user_id
  -> users.person_id
  -> Cadence User
```

The existing runtime lookup remains the VS-001-compatible
`users.auth_user_id` bridge. `authentication_identities` remains the
replaceable identity history and must agree with that bridge. Login identifier
and email are mutable authentication data, not stable Person identity.

The procedure must fail closed when an active provider subject is mapped to a
different Person, a Cadence User is mapped to a different Auth subject or
Person, more than one active identity conflicts for a Person, or the intended
Person cannot be determined by an exact trusted mapping. Relinking an identity
to an existing Person must not recreate or restore a historical project
membership.

## 9. Project bootstrap requirements

The manifest identifies one real pilot project by a stable operator-controlled
project key/ID and exact intended project attributes. The procedure must:

- create the project only through a Projects-owned operator contract when it is
  absent;
- verify exact compatible state when it already exists;
- set/verify a pilot-appropriate lifecycle state and required project fields;
- set/verify the schema-required `owner_user_id` projection consistently with
  the intended Owner's Cadence User, without treating that field as current
  authorization evidence; and
- verify a current Project Health row and required initial state before
  activation.

The existing schema already contains the project and Project Health structures;
no VS-004 migration is authorized by this contract. The M1 procedure must not
claim C01.2's full atomic project/health initialization unless an existing or
new module-owned contract proves that atomic outcome. If compatible project
state cannot be established safely, the run stops before mutation.

## 10. Membership and role requirements

Every pilot role holder must first have an active canonical Person-to-Project
membership effective for the pilot rehearsal. New memberships must use the
existing atomic `add_project_member` contract, which creates:

```text
ProjectMembership
  +
initial PROJECT_MEMBER ProjectRoleAssignment
```

The membership grantor and initial role assigner are the same stable Person
required by the existing contract. The membership period is the canonical
half-open interval `[effectiveFrom, effectiveTo)`; the default pilot is
open-ended unless the manifest explicitly defines a safe bounded scenario.

Ordinary role changes to Observer or Auditor, when included, must use the
existing ordinary-role contract. They must not insert a second overlapping
ordinary assignment or write retained legacy fields.

The following remain authoritative and must not be changed or repurposed:

```text
user_id, role_id, joined_at, status, created_by
```

They are frozen VS-001 compatibility/provenance fields under R03. New
Person-only memberships use canonical Person, period, status, grantor, role,
event, and audit mechanisms.

## 11. Protected-role requirements

The pilot project must have exactly one current effective holder for each
required protected responsibility:

```text
PROJECT_OWNER
PROJECT_MANAGER
PROJECT_SPONSOR
```

The default Owner, Manager, and Sponsor assignments must be active, project
scoped, period-aligned, and held by intended pilot memberships. Bootstrap
protected-role semantics are:

- if no effective protected holder exists, the canonical
  `transfer_project_protected_role` appointment contract may establish the
  first holder;
- if the intended holder already exists with an exact compatible assignment
  and ledger history, bootstrap must reuse and verify it;
- if a different effective holder or contradictory protected-role history
  exists, preflight fails with no mutation; and
- bootstrap must not transfer a protected role merely to force the database
  into manifest shape.

Direct assignment inserts, separate outgoing removal, or direct update of
protected history are forbidden. A genuine later protected-role transfer is a
separately authorised governed operation using the existing canonical
contract; it is not implicit bootstrap reconciliation.

Every protected assignment must have its matching immutable transfer-ledger
entry, including incoming assignment, optional outgoing assignment,
authorising Person, nonblank reason, effective time, creation time, and
correlation ID. A conflicting holder, missing ledger entry, divergent ledger
facts, or incompatible history is a hard preflight failure. It must not be
repaired by overwriting history.

Protected-role authority remains permission-based. The coordinator may use
the operator's declared governance authority to prepare an empty pilot, but
consuming modules must continue to ask `ProjectAuthorisationService` for
permission decisions.

## 12. Optional Observer/Auditor treatment

Observer and Auditor are optional pilot scenarios. If included:

- the Person receives an active canonical membership;
- the ordinary role is established through the canonical ordinary-role
  mechanism;
- Observer is verified as read-only; and
- Auditor is verified as read-only, with `audit.view` only where the current
  permission model grants it.

Neither role may create, update, delete, post Discussion content, change
membership, transfer a protected role, or gain authority because a frontend
control is hidden. Advanced Auditor interfaces remain outside this slice.

## 13. Preflight requirements

Preflight is a complete read-only validation of the entire manifest, target,
and existing state. It must finish successfully before any mutation, including
the creation or password update of an authentication account.

It must validate:

- manifest schema, required fields, stable identifiers, allowed role values,
  user count, distinct default role holders, timestamp/period syntax, and
  nonblank reasons;
- explicit environment and Supabase target, with the existing environment
  safety checks and an explicit safe-target marker;
- duplicate intended login identifiers and duplicate manifest Persons;
- existing Auth-account multiplicity and exact provider-subject identity;
- existing Person, Cadence User, and authentication-identity consistency;
- wrong-Person or wrong-Cadence-User mappings;
- existing project and Project Health compatibility;
- every intended membership's project, Person, period, lifecycle, grantor,
  membership provenance, and canonical ordinary-role state;
- required protected holders, protected-role cardinality, assignment periods,
  transfer-ledger completeness, and role/event/audit provenance;
- project isolation assumptions and the availability of negative access
  scenarios; and
- absence of any need to mutate retained legacy fields or destructive history.

Any read error, unknown state, duplicate, contradictory row, unsafe target, or
malformed configuration is a preflight failure. A successful preflight result
must be attributable to the manifest version/hash, target, operator Person,
and run correlation ID without recording secrets.

## 14. Fail-closed and conflicting-state behavior

The procedure must stop with no mutation when it detects, at minimum:

- duplicate intended login identities;
- duplicate or conflicting Person identity;
- an authentication identity mapped to the wrong Person;
- a Cadence User mapped to the wrong Auth subject or Person;
- missing Owner, Manager, or Sponsor membership/leadership;
- multiple or conflicting effective protected-role holders;
- incompatible existing project or Project Health state;
- incompatible membership grantor, period, lifecycle, or historical provenance;
- an incorrect project membership or role assignment;
- wrong environment, wrong Supabase target, or unsafe operator target; or
- malformed pilot manifest/configuration.

The error must identify the category and safe remediation boundary without
revealing credentials or project data to an unauthorized caller. A failed
preflight must not partially prepare earlier manifest entries. Operational
remediation of a real conflict is a separately authorized action and is not
implicit in bootstrap rerun.

## 15. Repeatability and idempotency

The operator procedure must be safe to run repeatedly against the same
intended state. After one successful run, a second successful run must verify
and reuse state rather than duplicate, overwrite, close, transfer, or rewrite:

- Person rows;
- Cadence User rows;
- authentication identities or Auth accounts;
- the project and current Project Health state;
- memberships and ordinary role assignments;
- protected assignments and transfer history; or
- domain-event, audit, and provenance history.

Rerun must not reset an existing password, rewrite mutable identity metadata,
change historical timestamps, generate duplicate canonical events, or create a
new transfer when the intended protected holder already matches. Idempotency
must be verified by stable identifiers, exact canonical state, and relevant
history, not by a successful command exit alone.

### Failed execution and safe resume

Whole-plan preflight must succeed again before the first mutation of every
execution attempt. If an execution step fails after mutation has begun, the
procedure must stop further execution and record the failed step, run, and
correlation evidence without secrets. It must not compensate with `DELETE`,
historical rewrite, membership termination, role closure, or protected-role
transfer.

On rerun, the complete preflight is required again. State already created may
be reused only when it is an exact compatible subset of the intended manifest
and satisfies canonical provenance and history. Contradictory partial state is
a hard failure requiring separately authorised remediation. A successful
resume remains idempotent and must not duplicate events, assignments, transfer
history, identities, or audit/provenance records.

## 16. No destructive reconciliation rule

Bootstrap is additive-or-verify only. It must not use `DELETE`, `TRUNCATE`,
historical update, broad upsert, legacy-field rewrite, membership termination,
role closure, or protected-role transfer to force an incompatible database into
the manifest shape.

In particular, it must preserve the R03D protections for membership identity,
grantor provenance, role assignment history, protected transfer history, and
the retained VS-001 fields. An incompatible existing row is reported for
operator/governance remediation; it is never silently repaired by bootstrap.

## 17. Access verification matrix

Verification must assert permission decisions and endpoint outcomes. It must
not infer authority from role-name checks in consuming code.

| Scenario | Required result |
|---|---|
| Owner, Manager, Sponsor, Member access project | `project.view` decision allows access. |
| Owner, Manager, Sponsor, Member, Observer, Auditor member view | `member.view` decision and Members read are allowed where the scenario is included. |
| Owner/Manager/Member Discussion write | `message.create` is allowed by the current permission baseline. |
| Sponsor Discussion write | Denied by the current permission baseline unless a separately governed module policy changes it. |
| Observer/Auditor Discussion write | Denied; no message persists. |
| Owner/Manager ordinary member management | Only the current explicit member permissions allow the operation. |
| Owner/Sponsor protected-role operations | Decisions use the current protected-role permission codes and canonical transfer boundary. |
| Nonmember or ended/expired member | No project authority; protected-resource concealment/denial remains intact. |
| Unauthenticated request | `401 UNAUTHENTICATED`. |

The matrix must include at least one positive and negative authenticated API
check for each included role scenario and must verify no denied operation
creates a membership, assignment, event, audit row, or business record.

## 18. Project isolation and concealment verification

The pilot project must be isolated from another project and from a nonmember.
Verification must prove that:

- an authorized pilot Person can access only the configured project through the
  intended membership and permission decision;
- a nonmember cannot read the pilot project or infer protected project
  existence through a protected endpoint;
- a Person authorized for another project does not gain pilot-project access;
- role differences are project-scoped; and
- no pilot manifest entry grants universal project access merely because the
  Person is an operator or platform administrator.

Where the default one-project pilot has no second real pilot project, the
negative check may use an existing controlled test project or an isolated
runtime fixture. It must not add a second real pilot project merely to satisfy
this verification.

## 19. API-only business-access verification

Browser business data must travel through `/api/v1` and the owning application
services. The operator procedure may use server-side provider/admin and
module-owned persistence contracts; it must never place a service-role key in
the browser.

Browser/network evidence must show zero direct Supabase business-table or
business-RPC calls for pilot project, membership, role, Discussion, Task, or
Audit data. Authentication/session calls are not business-data authority.

The check must preserve `ProjectAuthorisationService` as the sole application
project-authority boundary and preserve database/RLS defense in depth.

## 24. Pilot Activation relationship

VS004 supplies the prepared users, identity mappings, project, memberships,
protected roles, optional read-only scenarios, and VS004-owned access evidence
needed by the Pilot Activation Gate. VS004 closure does not authorize live
operation by itself.

Activation additionally requires stable frontend/API deployment and secure
environment configuration, supervised worker execution, backup and isolated
restore, support ownership, recovery/escalation instructions, and the complete
M1 multi-user rehearsal. Those conditions are governed by the M1 contract and
the VS005/VS006 slices.

## 25. Explicit boundary with VS005 and VS006

VS005 owns the pilot deployment target, frontend/API hosting/process boundary,
worker scheduling, supervision, and runtime execution model. VS004 may require
an explicit target preflight but must not select or implement the hosting or
scheduling solution.

VS006 owns backup technology, restore proof, support ownership, incident and
recovery procedure, and operational rehearsal. VS004 may require their
activation evidence but must not choose backup technology, perform the restore
proof, or redefine support ownership.

## Contract freeze decision

The existing schema and canonical VS-002 mechanisms are sufficient to design
VS004 without a migration or database reset. Implementation must first prove
that a module-owned contract cannot satisfy any structural need before
proposing a forward migration. A reset is not part of VS004.

VS004-02 is the next checkpoint: define the pilot manifest and implement its
pure whole-plan preflight with zero-mutation failure tests before adding any
bootstrap mutation path.
